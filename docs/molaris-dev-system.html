¿Qué es el Molaris Dev System?

El problema que resuelve

Eres un dev solo con trabajo de día, construyendo un producto dental sin ser dentista. Hasta ahora has avanzado por intuición — sin saber bien qué tiene más valor para Galana, qué está roto, o qué hacer primero. El resultado: features a medias, sin backlog claro, y sensación de estancamiento.

Este sistema te da estructura sin burocracia. Un equipo virtual de agentes IA con roles claros que generan trabajo, lo trackean en GitHub, y lo ejecutan — mientras tú aprobás el rumbo y hablás con tu hermana cuando hay que decidir algo clínico.

Principios del sistema

  • Outcome-first: primero definir qué debe lograr el dentista, después codear
  • Discovery antes de dev: si hay dudas clínicas, consultar al dentista antes
  • GitHub Issues como backbone: un issue = una unidad de trabajo
  • Tú aprobás, los agentes ejecutan: nunca se implementa sin tu OK
  • Sprints cortos: 1 semana, 2-3 issues máximo dada tu disponibilidad

Los actores

  • Juan — Dev, Product Owner, aprueba todo el backlog
  • dentistas (stakeholders clínicos) — Stakeholder clínica, valida lógica dental
  • Discovery Agent — Genera preguntas y mapea outcomes
  • Auditor Agent — Revisa el código y detecta deuda técnica
  • Planner Agent — Crea issues estructurados en GitHub
  • Dev Agent — Implementa features y fixes
  • QA Agent — Valida que todo funcione antes del merge

Metodología Outcome-First (inspirada en SPDD)

El error más común es empezar por "¿qué feature hago?" La pregunta correcta es "¿qué debe lograr el dentista que hoy no puede lograr bien?" Esto es lo que hace que el producto valga algo para Galana.

Regla #1: Si la implementación requiere saber algo de lógica clínica (ej: cómo se registra un tratamiento, qué datos necesita una ficha, qué flujo sigue un paciente), no codies hasta validar con el dentista. Un issue de discovery vale más que código que hay que rehacer.

Plantilla: Preguntas para el dentista (Discovery Session)

🩺 Guía: Cómo hacer una Discovery Session con el dentista
ANTES DE LA REUNIÓN (Discovery Agent genera esto): ───────────────────────────────────────────────── Área: [ej: Odontograma] Duración estimada: 20-30 min Objetivo: entender el flujo real del dentista hoy PREGUNTAS BASE (el Discovery Agent las personaliza por área): 1. ¿Cómo registras hoy el estado de cada diente? (papel, sistema, etc.) 2. ¿Qué estados posibles tiene un diente en tu práctica? (sano, caries, fractura, implante, corona, extracción, etc.) 3. ¿Necesitás anotar algo más allá del estado? (urgencia, nota clínica) 4. ¿En qué momento del flujo lo usás? ¿Antes o durante la consulta? 5. ¿Qué información necesitás ver rápidamente de un paciente nuevo? DURANTE LA REUNIÓN: ───────────────────────────────────────────────── □ Tomá notas textuales (no interpretés, anotá exacto lo que dice) □ Si algo no tiene sentido, pedí que te muestre cómo lo hace hoy □ Preguntá siempre: "¿Eso es siempre así, o hay excepciones?" DESPUÉS DE LA REUNIÓN (Planner Agent convierte en issues): ───────────────────────────────────────────────── Pegá las notas → el Planner Agent crea los issues con criterios de aceptación

GitHub Issues — El Backbone

Cada unidad de trabajo es un issue. Nada se implementa que no tenga issue. El Planner Agent los crea, Juan los aprueba, y los Dev Agents los cierran con un PR.

Sistema de Labels

Label Cuándo usarlo Quién lo crea
outcome Issue que describe un objetivo de negocio/usuario, no una feature concreta Discovery / Planner Agent
feature Nueva funcionalidad a implementar Planner Agent
bug Algo que está roto o se comporta mal Auditor / QA Agent
debt Código que funciona pero necesita mejorarse (rendimiento, arquitectura, tests) Auditor Agent
discovery Hay algo que investigar o decidir antes de codear Discovery Agent
clinical Requiere validación del dominio dental (preguntarle al dentista) Discovery Agent
qa Issue de testing o validación QA Agent
infra Deploy, CI/CD, infraestructura Cualquier agente

Labels de Prioridad y Estado

priority:high priority:medium priority:low · status:ready status:needs-discovery status:blocked

Template de Issue

📝 Template: Cómo escribe un issue el Planner Agent
**Título:** [Verbo] + [qué] + [para quién/dónde] Ejemplo: "Mostrar historial de tratamientos en ficha del paciente" **Labels:** feature, priority:high, status:ready **Outcome relacionado:** → La dentista puede revisar el historial completo de un paciente en <1 min **Descripción:** [Contexto en 2-3 líneas: por qué esto importa para Galana] **Criterios de aceptación:** - [ ] [Qué debe poder hacer el usuario] - [ ] [Qué debe mostrar el sistema] - [ ] [Casos edge: qué pasa si no hay datos, si hay muchos, etc.] - [ ] [Criterio de performance si aplica] **Notas técnicas:** - Archivos afectados: [lista si se sabe] - Dependencias: [otros issues si aplica] - Advertencias: [algo que hay que tener cuidado] **Discovery pendiente:** [si hay label clinical, qué hay que preguntarle al dentista]

Quick Reference — Cómo empezar cada sesión de trabajo

🌅 Al empezar una sesión de trabajo

  1. Mirá los issues abiertos en GitHub (gh issue list)
  2. Si no hay issues status:ready → pedile al Planner Agent que los cree
  3. Si hay issues status:needs-discovery → agendar una sesión de discovery con el dentista
  4. Tomá un issue status:ready → invocá el Dev Agent

🌆 Al terminar una sesión de trabajo

  1. Si terminaste el issue → invocá el QA Agent
  2. Si QA pasa → abre PR a dev
  3. Si es viernes → invocá el Auditor Agent
  4. Actualizá el status del issue en GitHub

📟 Comandos rápidos desde terminal

# Ver issues abiertos del backlog gh issue list --label "status:ready" # Ver qué necesita discovery con el dentista gh issue list --label "status:needs-discovery" # Crear issue rápido (el Planner Agent hace uno más completo) gh issue create --title "[título]" --label "feature,priority:high,status:ready" # Ver el estado del branch actual git status && git log --oneline -5 # Push a dev (nunca directo a main) git push origin dev

🚨 Reglas que nunca romper

  • 🔴 Nunca codear algo clínico sin validar con el dentista primero
  • 🔴 Nunca pushear directo a main — siempre dev → beta → main
  • 🟡 Siempre crear el issue antes de implementar — aunque tarde 5 min
  • 🟡 El QA Agent valida antes de todo merge — no te saltés este paso
  • 🟢 Podés tomar cualquier issue sin importar el orden si está en status:ready
